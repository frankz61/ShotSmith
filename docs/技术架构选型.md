## 1. 选型原则

需求里有三条硬约束直接决定技术取向，本文所有选型都围绕它们：

| 原则 | 含义 | 对架构的影响 |
|---|---|---|
| **还原度优先** | 商品款式/颜色/材质/Logo 不能被 AI 改变 | 核心生成环节优先选"商品保持"能力强的方案，并强制做还原度校验 |
| **先买后建** | MVP 用商用 API 跑通闭环，再评估自建 | 模型能力必须**抽象成可替换的适配层**，不与某家 API 绑死 |
| **异步可扩展** | AI 生图耗时长（秒~分钟级） | 请求与计算解耦，任务队列 + Worker 横向扩展 |

一句话：**Python 负责"编排"，把抠图、生成、校验、打包串成可观测的流水线；具体模型能力可插拔。**

## 2. 技术栈总览

| 层 | 选型（MVP） | 理由 | 备选 / 演进 |
|---|---|---|---|
| Web/API 框架 | **FastAPI** | 原生 async、Pydantic 校验、自动 OpenAPI 文档，AI 服务事实标准 | Flask（同步、不推荐）|
| 异步任务队列 | **Celery + Redis** | 生态成熟、重试/进度/路由完善，匹配"批量异步" | ARQ（轻量、纯 async，单机 MVP 可替代）|
| 消息/缓存 | **Redis** | 同时做 Celery broker 和结果缓存 | RabbitMQ（更重）|
| 元数据库 | **PostgreSQL** | 任务/素材元数据、状态机、JSON 字段 | SQLite（极简 MVP 起步，零依赖）|
| 对象存储 | **本地 FS（MVP）** | 起步零成本 | MinIO / 阿里 OSS / S3（上量后必换）|
| **抠图/分割** | **rembg（BiRefNet）** | 开源、自建、单图成本≈0、质量够用 | 商用抠图 API；SAM 系（异形/垂类）|
| **背景/场景生成（核心）** | **商用"商品图"API** | 还原度与稳定性开箱即用，省工程 | 自建 SD/Flux + ControlNet/IP-Adapter（二/三期降本）|
| Prompt 扩写 | LLM API（二期） | 把"木桌+阳光"扩写为专业提示词 | 本地 LLM |
| 海报/文案排版 | Pillow / HTML→图 + 模板（二期） | **文字走模板渲染，不靠 AI 出图**，避免乱码 | 设计类 API |
| 超分/补光 | Real-ESRGAN（后续） | 达到上架清晰度 | 商用增强 API |
| **还原度校验** | **DINOv2 / CLIP 向量相似度** | 比对输出商品区与原图，低于阈值打标人工复核 | 感知哈希 + 特征匹配（更轻）|
| 前端 | **Gradio / Streamlit（MVP）** | Python 原生，几天出可点的闭环 Demo | React + Vite（二期正式前端）|
| 配置 | pydantic-settings + `.env` | 类型安全配置 | —— |
| 打包/部署 | Docker + docker-compose | 一键拉起 API/Worker/Redis/PG | K8s（上量后）|
| 测试 | pytest + httpx | 单测 + API 测试 | —— |

> 依赖管理建议 **uv**（或 Poetry）；代码规范 **ruff + black + mypy**。

## 3. 核心环节深入：商品还原度方案（选型的胜负手）

这是整个系统**唯一不可妥协**的点。"换背景不改商品"有三条技术路线：

| 路线 | 做法 | 还原度 | 工程量 | 单图成本 | 适用阶段 |
|---|---|---|---|---|---|
| **A. 商用商品图 API** | 上传商品图+提示词，厂商保证主体保持 | ★★★★☆ | 低 | 中（按次计费） | **MVP 首选** |
| **B. 抠图 + 受控生成（自建）** | rembg 抠主体 → SD/Flux + IP-Adapter/ControlNet 只生成背景 → 合成 | ★★★★☆（需调参） | 高（GPU+管线） | 低（摊薄后） | 二/三期降本 |
| **C. 纯文生图** | 仅靠提示词生成整张图 | ★☆☆☆☆ | 低 | 中 | ❌ 不可用，商品会被"重画" |

**结论：MVP 走 A，把 B 作为同一适配接口下的第二个实现，待量起来后做 A/B 成本与质量实测再切换。** C 路线明确排除。

> 路线 B 的关键技巧：**抠图后的商品像素层在最终合成时原样贴回（或用 inpainting 只重绘背景区域）**，从机制上保证商品 0 篡改，比"祈祷模型不改"更可靠——这也是二期自建的核心价值。

## 4. 建 vs 买：决策矩阵

| 维度 | 买（商用 API） | 建（自建 SD/Flux） |
|---|---|---|
| 上线速度 | 快（天级接入） | 慢（周级搭管线、调参、压测） |
| 还原度 | 开箱较好 | 需自己调 ControlNet/IP-Adapter |
| 单图成本 | 按次付费，量大则贵 | 摊薄后低，但有 GPU 固定成本 |
| 可控/可定制 | 受厂商能力边界限制 | 完全可控、可微调垂类 |
| 合规/数据 | 图片出境/留存看厂商条款 | 数据不出本地 |

**推荐路径：MVP 用商用 API 验证业务闭环和市场 → 跑出真实日处理量后，用决策矩阵里的"单图成本×月量 vs GPU 固定成本"算盈亏平衡点 → 超过平衡点再投入自建。** 适配层保证这次切换不动业务代码。

## 5. 部署架构

**MVP（单机 / 一台带 GPU 的机器或纯 API 模式）：**

```
┌─────────────────────────────────────────────┐
│  docker-compose（单机）                        │
│                                               │
│  [Gradio/前端] → [FastAPI] → [Redis] ⇄ [Celery Worker] │
│                      │                    │   │
│                  [PostgreSQL]      [本地存储 /data] │
│                                           │   │
│                              调用 → 商用图像 API     │
└─────────────────────────────────────────────┘
```

**扩展期（上量后）：**
- API 与 Worker 分别水平扩容；Worker 按 GPU/CPU 任务分队列。
- 本地 FS → 对象存储（OSS/S3）；PG 主从；Redis 集群。
- 自建模型上线时，Worker 拆出独立 GPU 节点池。

## 6. 选型结论：MVP 技术栈清单

> 落地即用的一份清单，开发可直接照此初始化项目：

- **语言/运行时**：Python 3.11+
- **API**：FastAPI + Uvicorn
- **任务**：Celery + Redis
- **存储**：PostgreSQL（元数据）+ 本地 FS（图片）
- **抠图**：rembg（BiRefNet 模型）
- **生成（核心）**：商用"商品图"API（经适配层，首期接 1 家，预留第 2 家）
- **还原度校验**：DINOv2/CLIP 余弦相似度（先打标人工复核，不强卡）
- **图像处理**：Pillow + OpenCV（尺寸适配、合成、补阴影）
- **前端**：Gradio（验证闭环）
- **工程**：uv + ruff + mypy + pytest + Docker

## 7. 风险与待验证（上线前 PoC 清单）

| # | 待验证项 | 怎么验 | 风险 |
|---|---|---|---|
| 1 | 商用 API 的真实还原度 | 选 30~50 个真实品类样本跑对比，人工评分 | 厂商宣传 ≠ 实测，是 MVP 第一优先 PoC |
| 2 | 抠图对难例（毛发/透明/反光） | rembg vs 商用抠图 API 对比 | 难例边缘脏，影响合成 |
| 3 | 还原度校验阈值 τ | 用样本标注"可用/不可用"，找最佳分界 | 阈值太严漏放、太松误放 |
| 4 | 单图端到端成本与耗时 | 跑通后实测 | 决定建/买切换时机 |
| 5 | 去水印的合规边界 | 业务/法务确认 | 需求 §5 已标红，**不在工程内自行决定** |

> 模型与服务能力迭代很快，第 1/2 项的具体厂商选择以**当期实测**为准，本文不锁定品牌。
